# S1.2 · 界面开关不是执行边界

**本步用途：** 从前端熟悉的开关，追踪服务端是否真的限制动作。前置是 S1.1 的消息与执行区别。**目标：** 能沿同一请求解释“设置意图”和“执行检查”为什么需要分别存在。

## 完整示范：关掉工具，再观察

先选择 normal，取消“允许使用 read_doc”，再开始。合成脚本仍会返回工具请求，这是故意给服务端的反例；它不会因为没有 tools 说明就自动变得听话。

程序产生 blocked，executed 为 0。关键不是前端 checkbox，而是 `lab/reference.ts` 在工具分支检查 toolsEnabled。正常脚本、同一任务、同一工具请求，仅本次启用意图不同；对照开启时的工具执行事件。

顺着代码看 `lab/web/app.js` 提交 toolsEnabled，`lab/server.ts` 检查参数形状，`lab/reference.ts` 决定能不能执行。网页参数仍可被本机用户改写，这个演示不是企业身份授权体系。真正多用户权限是后续阶段的独立任务。

## 一个有依据的小变化

**用途：** 认识多条限制组合时的优先级。**依据：** 本课基线规定，最后一个模型轮次仍有工具请求时，整批不执行，因为没有后续轮次消费结果。**范围：** 指出是否执行，不猜下一次供应商回答。

将 maxTurns 设为 1，并选择“同一批重复请求”。请求一共有三个，重复策略会不会使前两个获得执行机会？

提示：先定位 `turn === maxTurns`，再看重复检查的位置。卡住时导师走一遍预算分支，不让你凭印象猜。

<details><summary>练习后核对依据</summary>
不会。预算检查先于所有工具执行和重复策略，这批 executed 为 0。它是本课明确选择的控制契约，不代表所有产品只能采用这种策略；改变策略要同时修改可解释的验收。
</details>

## 可运行实验

```sh
npm run demo -- --no-tools
npm run demo -- --scenario repeat --max-turns 1
```

两者应非零退出，分别是 blocked 与 exhausted；非零不等于程序崩溃。查看 result.json 的 executed 和事件，不只看 CLI 一句总结。相关回归在 tests/runtime.test.ts。

导师可以帮助你只改一处界面标签，让用户更清楚“本次运行允许工具”不等于永久授权；先写意图，再改代码，再验证不影响请求结构。不要借此开一个全栈权限项目。

收口：UI 表达意图，服务端实施本次约束；模型提议不产生权限。下一课处理“界面停止”和“后台确认停止”的区别。
