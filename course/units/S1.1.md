# S1.1 · 回答从哪里来

**本步用途：** 从一个完整小任务认识界面、程序、提供商与工具，避免只看到聊天气泡就以为任务完成。前置只需要知道浏览器和服务端会传递数据；不预读其他单元。

**目标：** 沿 `testing` 文档的一条内容，指出它何时进入下一轮消息，以及怎样核验最终回答。

## 先看一个完整示范

导师启动 `npm start`，在本机实验台保留默认任务，选择“读取依据后回答”。这是预写脚本，不是真实模型。先不要讲整个 reference.ts，也不要让学习者猜服务商输出。

![一份依据怎样进入回答](../assets/flow.png)

从 1 看起：网页把问题发送给本地服务。2 的“提供商”在本次是 scriptedProvider，它按教学脚本发出 read_doc 请求，并未自己读文件。3 的 invokeTool 检查请求，返回合成 testing 文档，其中写着 npm test。程序把这份结果与 call-1 关联，加入 messages。4 的再次请求已经包含工具结果，脚本再返回“运行命令：npm test，依据：[testing]”。

图是机制示意，不是本次运行记录。真正的本次数据在网页“查看这一步的数据”和本地 run id 对应结果中。

**代码只看三处：** `lab/tools.ts` 的 DOCUMENTS/invokeTool；`lab/reference.ts` 中追加 tool 消息的位置；`lab/providers.ts` 中脚本怎样消费上一条工具消息。工具查的是内存资料，不是实际磁盘；后续再学习文件工具。

“拿到结果”和“将结果送进下一次请求”是两步。本地出现文字并不会自动让远端看到它。这里采用显式 messages，不把这种接口使用方式泛化为所有模型都没有会话能力。

## 你来处理一个小变化

**为什么问：** 排查“程序读到了，模型却没有依据”的问题。**看什么：** 网页中第二次 model.requested 的 messages。**回答到什么程度：** 指出结果在哪一条消息，不必背协议名。

题目：结果在终端打印了，但没有加入下一次 messages，且没有其他传递渠道。能否说模型这次收到了这份结果？请指出缺失动作。

卡住时先让导师定位 tool 消息；仍不懂就并排看“只打印”和“加入再发送”两段，不重复猜题。

## 实验与证据

```sh
npm run demo
```

正常观察是两轮、一条工具执行、answered 和样例 matched；这是本脚本行为，不是任意真实模型的保证。`result.json` 保存终态和事件，`.learning/state.json` 不会自动变化。核对本次文件存在，不拿别人的 run id 代替自己的实验。

收口：模型/脚本给出请求，程序决定并执行工具，工具结果需要传递，最后仍要检查依据。下一课只改变工具开关和预算，看看谁保证“不执行”。
