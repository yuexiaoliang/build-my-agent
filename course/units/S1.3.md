# S1.3 · 结束了，还是完成了

**本步用途：** 避免用一个 success 布尔值掩盖不同事实。前置是前两课的执行链。**目标：** 能根据终态与证据说明发生了什么，还不能下什么结论。

## 先完整看一个“回答了但不合格”的例子

选择“没有读取依据就回答”。脚本返回 npm start，还附上看起来正式的 [testing] 引用。程序状态是 answered：确实产出了正文。独立样例检查 failed：命令不符，而且没有本次工具读取依据。

![四种完成不能互相替代](../assets/evidence.png)

先看第 2 框与第 3 框，区分生成状态和任务核验，再看第 4 框：即使样例检查 matched，也不能证明学习者会诊断一个新问题。`lab/check-result.ts` 只比较固定格式及来源记录，不是语义评分器，也不是泛化基准。

再选择“响应被截断”。正文可能看起来有内容，但 finishReason=length，工具不执行，状态 truncated。保留停止信号是程序的责任，不是让用户自己从半句话猜。

## 取消示范：点下去与确认回来

选择 slow，开始后点击停止。界面先写“已请求停止”，只有服务端返回 cancelled 终态才写确认。按 `web/app.js → /api/cancel → AbortController → run.finished` 带读，不要求首课就实现所有取消机制。

外层等待期限到达会得到 timed_out；不能因此断言任意外部服务或不合作的工具已经物理停止，更不能说副作用自动回滚。当前工具是只读内存查表，真实写操作在后续保护环境中另学。

## 一个变化

**为什么问：** 避免把网络故障显示成取消成功。**已知：** 点击取消后网络断了，没有收到服务端终态。**回答范围：** 给一句你会显示的准确状态，并说依据。

<details><summary>练习后核对依据</summary>
可以显示“取消请求已发出，服务端状态未确认”，不能写“全部停止”。缺少确认不证明没有停止，也不证明已经停止。这里评价状态与证据的对应，不要求固定措辞。
</details>

## 实验

```sh
npm run demo -- --scenario unsupported
npm run demo -- --scenario truncated
npm test
```

第一、二条预期非零。测试通过是程序证据，不是你的能力成绩。浏览器中的 slow/取消需实际操作；不能用单元测试替代 UI 体验验证。

收口：UI、运行、任务与学习各有证据。复访时换成“文件写成功但回执丢失”的情境，为恢复与幂等建立问题，不提前要求现在设计完整方案。
