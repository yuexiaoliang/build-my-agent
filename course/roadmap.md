# 课程路线：AI Application Engineering 为总目标

**总目标：成为能够独立设计、实现、诊断、评测和交付 AI 应用的工程师。Agent Harness 是重点技术纵深。**

学习仍从本地第一个问题和第一个小功能开始，不先阅读预制系统。课程不追某个框架清单，而是覆盖主要技术面并训练新技术出现后的迁移能力。

## 八阶段

| 阶段 | 作品怎样成长 | 主要能力 |
|---|---|---|
| S1 LLM 应用基础与 AI UX | 从最小模型调用成长为有结构化结果和真实状态的 Web AI 功能 | 从零完成一个可观察的 AI 功能，能解释模型请求、结构化结果、流式状态和前后端边界。 |
| S2 RAG 与 Context Engineering | 为作品加入可测量的知识检索与上下文组装 | 完成可测量的检索增强链路，能解释搜索、切分、重排、引用与上下文选择。 |
| S3 Agent Harness 与生态集成 | 加入工具、Agent Loop、工作流与 MCP 集成，形成 Harness 纵深 | 在已有应用上构建受控 Harness，理解工具、循环、状态、工作流、MCP 与集成边界。 |
| S4 可靠执行与安全边界 | 让副作用、权限、重试、长任务与恢复真正可控 | 让有副作用和长任务可控，覆盖校验、权限、隔离、取消、幂等与恢复。 |
| S5 多模态与 Realtime | 加入图像/文档与实时语音能力，完成多模态体验 | 交付至少一个图像/文档能力和一个实时音频交互，解释媒体链路、延迟与降级。 |
| S6 Evals 与 Observability | 建立 eval、回归和端到端 observability | 建立可重复评测与端到端 trace，用证据定位模型、检索、工具和系统问题。 |
| S7 模型选择与成本性能优化 | 用数据做模型选择、routing、缓存和成本性能优化 | 能在质量、延迟、成本和复杂度之间做有数据依据的模型与系统优化。 |
| S8 生产交付与独立迁移 | 补齐生产后端、部署和综合 Capstone，再做陌生场景迁移 | 完成可部署的 AI Web 产品，并在陌生需求中独立选择架构、验证方案和迁移边界。 |

完整技术覆盖见 [AI 应用工程技术地图](technology-map.md)。单元级目的、活动、验收、领域标签与直接前置只在 [catalog.json](catalog.json) 维护。

## 课程结构原则

- **广度覆盖主要 AI 应用技术面，深度重点放在 Harness、RAG、Evals/Observability 与完整产品交付。**
- 前端经验是优势：Streaming、Realtime、多模态交互、状态和审批 UI 会进入实际作品，而不是把学习者重新训练成只写脚本的人。
- RAG 不等于“接一个向量库”；会比较 lexical/vector/hybrid、chunking、metadata、rerank、citations，并用 eval 判断收益。
- Agent 不等于默认答案；每次加入 workflow、planning、subagent 或 MCP 都要说明比简单方案多解决了什么。
- Evals 与 observability 贯穿后半程，用同一套证据支持调试、模型选择、性能优化和上线判断。
- 多模态、Realtime、AI Backend、部署与安全都是正式主线，不再作为可有可无的附录。
- fine-tuning/蒸馏/合成数据学“何时值得做、如何验证”，不把大模型训练基础设施纳入本课程的主要纵深。

## 备课与状态

全部单元初始为 `planned`、`material=null`。它表示路线已经设计，但具体讲义、图片、代码和测试只在本地即将学习的当前小步准备和增量实现。

`planned → prepared` 只表示当前小步的示范、必要图文、练习依据和补救方式已经可用；实际授课后可记 `taught`。材料状态、代码完成、测试结果和学习证据仍分别记录。

当前 API、模型、协议和 SDK 会变化。导师在具体单元开始时核对当时官方文档和本地工具能力，不用 2026 年某个接口形状冒充永久知识。

[能力验收](assessment.md)决定“会不会”；[课程索引](catalog.json)决定“接下来学什么”；经过验证的实践可按 [portfolio](../portfolio/README.md) 整理成专业表达。
