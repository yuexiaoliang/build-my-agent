# 02.4 · 证据矩阵与对抗任务

> **本步问题**：闸门的判断怎么固化成可重复的证据？

> **蓝图对应**：第 02 章 工具契约（章验收：无效请求不执行）。

## 1. 目标与可观察任务

把 02.3 的手工验证固化成 `scripts/tool-checks.sh`：一组确定性用例（命令 + 期望退出码 + 期望输出模式），`npm run check:tools` 一键重跑，离线、免费、不经过模型。再加一个对抗练习：主动找一条能骗过闸门的请求。

## 2. 原理与执行轨迹

- 用例矩阵是闸门的**回归底线**：以后每改一次工具管线，先跑它再谈别的。它验证的是 Harness 行为（确定性），与模型行为（不保证）分开——这和 01.3"回放 / 真实分别标注"是同一条原则。
- 矩阵写完立刻抓到 02.3 的**误拒 bug**：`rel.startsWith("..")` 把合法文件名 `..notes.txt`（sandbox 里真实存在的回归文件）判成越界。修复：比较**首个路径段**——`rel.split(sep)[0] === ".."` 才算越界。
- 路径判断的两个经典坑同源：拿**字符串前缀**表达路径关系。`startsWith(sandboxRoot)` 会放行兄弟目录 `sandbox-evil`（02.3 已避开）；`startsWith("..")` 会误伤 `..notes.txt`（本步抓到）。**误放行和误拒都是 bug**——闸门要两边都对。
- 已知粗糙处（探测中发现）：空路径 `""`、`"."`、含 NUL 字节的路径都**通过闸门**，随后在 I/O 层以通用错误（退出码 5）失败——不是绕过，但错误分类粗糙，留待第 11 章。

## 3. 实现与差异导读

- `scripts/tool-checks.sh`：11 项用例；`check` 函数按"期望退出码 + 输出含指定文本"判定，最后汇总通过/失败数并以非零退出码报告失败。
- `src/tools.ts`：`resolveInSandbox` 改为首段比较（修复误拒）。
- `sandbox/..notes.txt`：触发误拒的回归文件，留在矩阵里防复发。

失败路径：矩阵 11 项里有 8 项是拒绝用例，它们就是本步的失败路径清单。

## 5. 验证记录（回填）

- 修复前：`node src/cli.ts call read_file '{"path": "..notes.txt"}'` → 被误拒（退出码 6）；修复后矩阵 11 项全绿。
- 对抗任务：用 `ln -s .. sandbox/out` 建符号链接，再经 `out/package.json` 读到了仓库根文件——绕过复现成功。结论判断正确：程序检查的是请求时的路径字符串，不是解析后的真实路径；物理路径校验（realpath）留给第 06 章。
- 真实调用对照：让模型请求读 `/root/notes.txt` → 闸门拒绝——真实调用首次打到闸门（此前都是 `call` 直调）。
- 自由搜索其他误判无产出——开放搜索需要更具体的靶子。据此整理出误判藏身地图，供后续章节对照：① 词法 vs 物理（符号链接）；② 结构合法但不可执行（目录、空路径）；③ TOCTOU（检查与使用之间的时间差）；④ 编码边界（NUL、大小写）。
