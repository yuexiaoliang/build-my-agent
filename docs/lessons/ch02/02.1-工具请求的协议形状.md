# 02.1 · 工具请求的协议形状

> **本步问题**：模型想用工具时，实际返回什么？
> **前置**：01.3 离线回放（fixture 与 replay）。
> **蓝图对应**：第 02 章 工具契约（模型请求如何成为合法行动？）。
> 说明：讲义基础设施建立晚于本章，本页在完成后据当时的真实运行证据回填整理；代码快照见提交 `e129785`（`课程(02.1)`）。

## 1. 目标与可观察任务

定义两个只读工具（`list_files`、`read_file`，操作 `sandbox/` 里的合成练习文件），`ask --tools` 把工具定义放进请求。运行时能观察到：模型返回的 `tool_calls` 原文形状（`index`、`id`、参数原文）；本步**刻意只解析、不执行**——执行与校验在 Harness 一侧，是后面两小步的事。

## 2. 原理与执行轨迹

- 工具定义放在请求的 `tools` 字段：`type: "function"` + `name` / `description` / `parameters`（JSON Schema）。这是给模型看的"我能做什么"说明书。
- **模型不能执行工具，只能请求**。它返回的是一段结构化数据，行动与否由 Harness 决定。
- 工具请求在 `choices[0].message.tool_calls`，其中 `function.arguments` 是 **JSON 字符串**——原文保留、不预先解析（何时解析是 02.2 的决策）。
- **不能假设 `content` 的形状**：同一提供商两次实测，一次是空字符串、一次带叙述文字，两者还可能同时存在。按"content 必为空"写校验会漏掉真实情况。
- 旧解析逻辑遇到这次真实响应**不是报错而是静默吞掉**：空字符串通过了类型检查，程序安静打印了一个空回答。静默失败比崩溃更危险——没有 fixture 回放，很难发现。
- 录制发生在解析之前（01.3 的设计），所以预期之外的响应也能成为回放材料；这一步顺手为 02.2/02.3 留下了工具调用的基线 fixture。

## 3. 实现与差异导读

- `src/tools.ts`：`list_files` / `read_file` 两个工具定义（含参数 schema）。
- `src/model.ts`：`sendChatRequest` 接受可选 `tools`（请求与录制都保留它）；`parseChatResponse` 增加 `toolCalls` 字段，`readToolCalls` 保留参数原文。
- `src/cli.ts`：`ask --tools`；`replay` 打印原请求带的工具与解析出的工具请求。
- `sandbox/notes.txt`、`sandbox/todo.md`：合成练习文件。

## 4. 验证

真实运行（有费用）：

```bash
node src/cli.ts ask --tools --record fixtures/ch02/toolcall.json "sandbox/notes.txt 里写了什么？"
```

**预测题（先写下判断，再运行）**：如果模型返回了 `tool_calls` 且 `content` 是空字符串，当时的旧解析代码（只认 `choices[0].message.content` 的文本）会报"缺少 choices[0].message.content"吗？程序的外在表现是什么？

离线回放（免费）：

```bash
node src/cli.ts replay fixtures/ch02/toolcall.json
```

失败路径 / 回归：回放 01.3 的旧 fixture（`fixtures/ch01/ask-success.json`），确认文字回答路径不受工具解析的影响。

## 5. 验证记录（回填）

1. 真实调用 + 录制（旧解析器）：HTTP 200，`content: ""`，`tool_calls[0].function.arguments = "{\"path\": \"notes.txt\"}"`（`fixtures/ch02/toolcall.json`，416 tokens）。
2. 回放该 fixture：解析出 `read_file`（id 保留、参数原文保留），退出码 0——离线回放。
3. 回归：回放 01.3 旧 fixture，文字回答路径不受影响——离线回放。
4. 再次真实调用：这次 `content` 带叙述文字、与 `tool_calls` 同时存在；耗时 2266 ms——真实运行。

预测与实测落差：预测题的事先判断是"会报缺少 content 的错"——走查逻辑对（非字符串必抛该错），错在前提：该提供商返回的是空**字符串**，通过了类型校验，旧代码安静输出空回答。教训：分支的触发条件不能靠推测的字段形状，要用实测数据。另一个小插曲：观察过程中出现过一行 `Cannot read properties of undefined`，那是"cli 已期待 toolCalls、解析器还没给"的改造中间态，不代表旧程序行为。

## 6. 小结

工具请求只是数据：`tools` 是说明书，`tool_calls` 是请求单，`arguments` 是未拆封的字符串。请求已经能看清了，下一小步让它真正变成行动——并亲眼看看没有闸门时会发生什么。
