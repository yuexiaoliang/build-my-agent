# 04.2 · 截断与 finish_reason

> **本步问题**：模型输出被长度上限切断时，Harness 会把半个回答当成完整结果吗？
> **前置**：04.1 的适配层与丢弃清单（`finish_reason` 是被丢弃字段之一）。
> **蓝图对应**：第 04 章（"截断"是本章验收点之一；"不把损坏输出当成功"）。

## 1. 目标与可观察任务

- `parseChatResponse` 开始读取 `finish_reason` 并把它带进 `ChatResult`；值为 `length`（被截断）时输出明确标注，不再无声通过。
- 真实调用观察一次真实截断：请求里把 `max_tokens` 压到很小（输出 token 很少，费用低）。
- 离线手术对照：把已有 fixture 的 `finish_reason` 改成 `length`，回放对比处理前后的差别。

## 2. 原理与执行轨迹

新术语：**finish_reason**——服务端对"这条响应为什么结束"的声明。常见值：

| 值 | 含义 | 响应完整性 |
|---|---|---|
| `stop` | 模型自己说完了 | 完整 |
| `tool_calls` | 正常请求工具（03 章每轮都是它） | 完整 |
| `length` | 撞到 `max_tokens` 或上下文上限，被切断 | **不完整** |

截断的破坏力在于**看起来正常**：文字是通顺的半句话；工具参数是半截 JSON。两种截断的现状不同：

- 文字截断：目前完全无声——半截话直接打印、回填，后续推理建立在半句话上。
- 参数截断：会撞 02.3 的闸门（`参数不是合法 JSON`），但报错原因会把"被截断"误导成"模型写了坏 JSON"。

核心区分：`stop` / `tool_calls` / `length` 是三种不同的真相。把 `length` 当 `stop` 处理，就是本章要消灭的"把损坏输出当成功"的第一种形态。

## 3. 实现与差异导读

计划改动（行号课后回填）：

- `src/model.ts`：`ChatResult` 增加 `finishReason`；`parseChatResponse` 从 `choices[0].finish_reason` 读取。
- `src/model.ts` / `src/cli.ts`：`sendChatRequest` 支持可选 `max_tokens`，CLI 加 `--max-tokens`（为了能用真实调用制造截断）。
- `src/cli.ts`：`finishReason === "length"` 时的处理动作——由本步设计题定。

## 4. 验证

真实运行（低费用，`max_tokens` 很小；**录制路径开课时定为 `fixtures/ch04/` 下新文件并现场登记**——真实录制不预制）：

```bash
node src/cli.ts ask --max-tokens 16 --record <开课时确定并登记> "用 300 字详细解释什么是 Agent Harness"
```

离线回放（手工改造，非真实录制）：

```bash
node src/cli.ts replay fixtures/ch04/surgery-finish-length.json
```

**设计题**：确认截断后 Harness 应该——(a) 当失败停止；(b) 标注后继续当正常结果用；(c) 自动追加请求请模型续写？选一个，一句话说它的代价。

**预测题**：`--max-tokens 16` 的真实运行里，被切断的除了文字还有什么？（提示：看用量行。）

失败路径：截断的文字结论被回填进后续步骤，后续推理建立在半句话上——而且没有任何输出提示这件事发生过。
