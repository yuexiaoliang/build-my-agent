# 03.1 · 工具结果回填与调用 ID 关联

> **本步问题**：工具执行完之后，模型怎样才能看到结果并继续行动？
> **前置**：02.1–02.4 工具契约与校验闸门；01.2 第一次真实调用与错误码。
> **蓝图对应**：第 03 章 Agent Loop（如何根据观察继续行动？）。
> 说明：讲义基础设施建立晚于本步，本页在完成后据当时的真实运行证据回填整理。

## 1. 目标与可观察任务

改造前：模型请求 `read_file`，工具结果只打印在本机终端，模型看不到，用户要的总结没有出现。

本步后：执行完工具，Harness 把结果**回填**进 messages 再发一轮请求——模型基于文件内容给出总结。运行时可以观察到：一个进程里出现两轮真实调用，且第二轮输入 tokens 比第一轮多。

## 2. 原理与执行轨迹

模型没有记忆：每次调用都是独立的 HTTP 请求。所以"让模型看到结果"不能靠"告诉它"，只能把历史装进下一轮的 `messages` 重新发过去。

回填的最小结构（三条消息缺一不可）：

| 顺序 | role | 内容 | 关键字段 |
|---|---|---|---|
| 1 | user | 原始问题 | — |
| 2 | assistant | 模型上一轮原话（文本可以是空字符串） | `tool_calls[]`：每个调用的 `id` 在这里定义 |
| 3 | tool | 工具结果，或被拒绝的原因 | `tool_call_id` 指回上面那个 `id` |

- id 关联是**服务端强制的结构校验**：只发 tool 消息、缺少带 `tool_calls` 的 assistant → HTTP 400：`Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`。请求到不了模型。
- 被校验闸门拒绝的调用也要回填（`tool_call_id` + `已拒绝：原因`），否则 id 配对断裂，下一轮同样 400。
- 代价可见：第二轮请求输入 464 tokens > 第一轮 360——无记忆意味着每轮重发全部历史（第 14 章处理压缩与缓存）。

## 3. 实现与差异导读

- `src/model.ts`：`ChatMessage` 改为联合类型——`user`/`system` 纯文本、`assistant` 可带 `toolCalls`、`tool` 带 `toolCallId`；新增 `toWireMessage` 在发送前序列化为协议线格式（`tool_calls`、`tool_call_id` 这类下划线命名只出现在线上，应用内部用驼峰）。
- `src/cli.ts`：执行完工具后收集 tool 消息（被拒绝的也收集），组装 user + assistant + tool 三条消息发起第二轮；第二轮若模型还要工具，此时只打印并停止（有界循环留到 03.2）。
- `scripts/orphan-tool-message.ts`：失败路径实验——故意跳过 assistant 消息，只发孤儿 tool 消息。

## 4. 验证

真实运行（有费用）：

```bash
node src/cli.ts ask --tools --record fixtures/chat-2026-09-15-loop-after.json \
  "sandbox/notes.txt 写了什么？用一句话总结"
```


## 5. 验证记录（回填）

- 改造前运行：模型请求 `read_file`，结果只在本机打印，用户要的总结没有出现（`fixtures/chat-2026-09-15-loop-before.json`）。
- 改造后：第二轮 messages = user(29 字符) + assistant(39 字符，含 tool_calls) + tool(76 字符)；模型基于文件内容给出总结；输入 360 → 464 tokens（`fixtures/chat-2026-09-15-loop-after.json`、`…-round2.json`）。
- 孤儿 tool 消息实验：HTTP 400 拒绝，错误原文见 `fixtures/chat-2026-09-15-orphan-tool.json`——证明 id 关联由服务端结构校验强制执行，不是模型自行解读。

## 6. 小结

"继续行动" = Harness 把历史（含工具结果）装进新一轮请求，`id` 把每条结果钉回对应的调用。下一小步（03.2）把固定两轮推广为有界循环。
