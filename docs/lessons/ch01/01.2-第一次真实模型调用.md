# 01.2 · 第一次真实模型调用

> **本步问题**：用最少依赖完成一次真实模型调用，并让"缺配置"和"请求失败"可以辨认。
> **前置**：01.1 任务形态与三层职责（同目录讲义）。
> **蓝图对应**：第 01 章 任务与模型。
> 说明：讲义基础设施建立晚于本章，本页在完成后据当时的真实运行证据回填整理；代码快照见提交 `02fc4b2`（`课程(01.2)`）。

## 1. 目标与可观察任务

一个最小 CLI：`ask "问题"` 发起一次真实调用并打印回答与用量。运行时能观察到：请求目标、模型名、会话 ID 在发送前先打印；四类失败各有专用退出码，互不难混淆。

## 2. 原理与执行轨迹

**一次模型调用就是一次 HTTP 请求**：`POST {baseUrl}/chat/completions`，请求体只有 `model` + `messages`，密钥走 `Authorization: Bearer` 头。不需要 SDK，也不需要框架。

**本地只能校验"填没填"，不能校验"对不对"。** 密钥是否有效、模型是否存在，只有服务端能判定——本地检查通过 ≠ 调用可用。

失败必须分类，否则排查无从下手：

| 退出码 | 类别 | 判定位置 |
|---|---|---|
| 1 | 缺配置（环境变量缺失） | 本地 |
| 3 | HTTP 错误（4xx/5xx） | 服务端 |
| 4 | 响应结构不可用 | 本地（解析时） |
| 5 | 其他网络 / 运行时错误 | 本地 |

两个只能从事故里学到的教训：

- **错误码不能想当然**：模型名不存在返回 **401** 而不是 400——网关把"模型不支持"归到了授权/路由一类。错误码分类也属于"服务端事实"，不能靠常识推断。
- **供应商有请求约定**：当前提供商要求 `x-opencode-session`（稳定会话 ID）请求头并自报 User-Agent，缺了直接 400。这类要求只能从服务端错误信息里学到。

## 3. 实现与差异导读

首个代码提交，三个文件：

- `src/config.ts` `readModelConfig`：必填三个环境变量（`MODEL_BASE_URL`、`MODEL_API_KEY`、`MODEL_NAME`），缺失时返回清单；只打印变量名和密钥长度，不打印值。环境变量优先于 `.env`——失败实验可以不改 `.env` 直接跑。
- `src/model.ts`：一次 POST，返回 `text / model / usage / elapsedMs / sessionId`（01.3 会把它拆成发送与解析两半）。
- `src/cli.ts` `ask`：先打印请求目标、模型、会话 ID，再打印回答与用量。

## 4. 验证

真实运行（有费用）：

```bash
node src/cli.ts ask "用一句话说明：模型与 Harness 各负责什么？"
```

**预测题（先写下判断，再运行）**：不改 `.env`，用环境变量覆盖跑一次：

```bash
MODEL_NAME=not-a-real-model node src/cli.ts ask "你好"
```

问题：请求到得了服务商吗？HTTP 状态码是多少——400 还是别的？哪一环能拦下这个错误？

失败路径：无 `.env`（或值为空）→ 退出码 1；`MODEL_API_KEY=invalid-key-for-test` → 观察状态码与服务端原文。

## 5. 验证记录（回填）

全部真实运行：

1. 无 `.env` → `缺少配置：MODEL_BASE_URL、MODEL_API_KEY、MODEL_NAME`，退出码 1（本地失败，未发请求）。
2. 首次真实调用 → HTTP 400 `Request is missing x-opencode-session`——暴露出供应商的会话头约定，补上后重试。
3. 成功：输入 49 + 输出 286 = 335 tokens，耗时 6181 ms；回答正确解释了模型与 Harness 的分工。
4. `MODEL_NAME=not-a-real-model` → HTTP 401 `Model not-a-real-model is not supported`（错误原文录制见 `fixtures/ch01/model-not-supported.json`）。
5. `MODEL_API_KEY=invalid-key-for-test` → HTTP 401 `Invalid API key.`

预测与实测落差：第 4 条事先预测"请求能到达服务商、由服务商报错"——方向成立；但预期状态码是 400，实测 401。再次印证：判据在服务端，本地怎么写校验都覆盖不到。

## 6. 小结

调用本身只是 HTTP；真正的工作在"失败可辨认"——四类退出码把排查入口分开。下一小步把真实响应留下来，不花钱也能反复验证解析路径。
