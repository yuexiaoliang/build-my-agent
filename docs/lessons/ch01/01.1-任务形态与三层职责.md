# 01.1 · 任务形态与三层职责

> **本步问题**：什么任务真的需要 Agent？Model / Harness / Environment 各负责什么？
> **前置**：无（课程第一步）。
> **蓝图对应**：第 01 章 任务与模型（哪些任务需要 Agent？）。
> 说明：讲义基础设施建立晚于本章，本页在完成后据当时的讨论记录回填整理；本步未产生代码。

## 1. 目标与可观察任务

本步不写代码。完成后能对任意给定任务判断形态——普通程序、固定工作流、还是需要 Agent——并用一句话说出判据；能说出模型、Harness、环境三层各自的职责。

## 2. 原理与执行轨迹

**判据只有一条：下一步做什么，是否必须依赖运行时才能拿到的证据。**

- 步骤在编码时就能全部写死 → 普通程序或固定工作流。哪怕任务很复杂——"300 个文件重排 import、跑全量测试、生成报告"步骤很多，但每一步都预先确定，仍是工作流。
- 下一步取决于现场证据（读到的内容、测试的结果、服务的响应）→ 需要模型现场判断，这才是 Agent。

边界在**控制流归属**：控制流写在代码里 = 工作流（哪怕内部调用了一次模型）；由模型逐步决定下一步 = Agent。"工作流内嵌一次模型调用"不算 Agent——控制流仍在代码手里。

**三层职责**：

| 层 | 职责 | 一句话 |
|---|---|---|
| Model（模型） | 判断与生成 | "想" |
| Harness（ harness/挽具 ） | 组织上下文、把模型输出变成合法动作、循环与边界、状态 | "管" |
| Environment（环境） | 文件、git、shell、测试、网络——动作真正发生的地方 | "发生" |

两个推论：

- **环境是唯一事实来源**：模型说"修好了"不算数，diff 与测试结果才算。
- Agent 不消除不确定性，只把每一步决定变成可执行、可观察、可中断的动作。

> 常见偏差纠正：任务"难"不等于需要 Agent（复杂但固定仍是工作流）；"偶发"提高的是不确定性，不是判据本身——偶发故障的排查之所以需要 Agent，是因为下一步检查什么取决于上一步看到的证据，有时连证据本身都要先造出来（加日志、构造可复现输入、缩小环节）。

## 3. 实现与差异导读

无代码。讲解对照例：读-改-写 `config.json` 的 timeout 属普通程序——步骤在编码时已定死。

## 4. 验证

课堂判断练习（先写下判断与理由，再讨论）：

- (a) 把 `config.json` 的 timeout 从 30 改成 60 并重启服务。
- (b) 300 个文件重排 import，跑全量测试，生成报告。
- (c) 用户反馈"导出功能偶发乱码"，需要定位并修复。

问题：各自属于哪种形态？判据是什么？(c) 的排查过程中，"证据"是从哪里来的？

## 5. 验证记录（回填）

课堂讨论确认：案例 (c) 无法固定步骤——排查涉及多个可能出错的环节，下一步动作依赖现场看到的证据，因此需要自主决策。讨论中收紧过一个表述：把"偶发提升了不确定性"修正为"不确定性是表现，判据是决策是否依赖现场证据"。

## 6. 小结

任务形态由控制流归属决定：能写死的写死（便宜、可靠），写不死的才交给模型逐步判断。下一小步做出第一次真实模型调用，并让失败可以辨认。
