# 02.1 · 工具请求的协议形状

- 日期：2026-09-14
- 本步问题：模型想用工具时，实际返回什么？
- 对应蓝图：第 02 章（模型请求如何成为合法行动？）
- 代码快照：公开仓库 `课程(02.1)`；fixture `fixtures/chat-2026-09-14-toolcall.json`
- 状态：有解释/预测证据（预测了失败位置；前提未应验，实测后修正）

## 核心结论（可迁移）

- 工具定义放在请求的 `tools` 字段（`type:"function"` + name / description / parameters(JSON Schema)），是给模型看的"我能做什么"说明书。
- 模型不能执行工具，只能**请求**；执行与校验在 Harness 一侧（本步刻意不执行）。
- 工具请求在 `choices[0].message.tool_calls`，其中 `function.arguments` 是 **JSON 字符串**——原文保留、不预先解析。
- 不能假设 `content` 的形状：同一提供商两次实测，一次是空字符串、一次带叙述文字，还可能同时存在——按"content 必为空"写校验会漏掉真实情况。
- 旧解析逻辑对这次真实响应的行为**不是报错而是静默吞掉**（空字符串通过类型检查，打印空回答）——静默失败比崩溃更危险。
- 录制发生在解析之前，所以预期之外的响应也能成为回放材料；这一步顺手为 02.2/02.3 留下了工具调用的基线 fixture。

## 关键代码与入口

- `src/tools.ts` — `list_files` / `read_file` 两个只读工具定义（含参数 schema）
- `src/model.ts` — `sendChatRequest` 接受可选 `tools`（请求与录制都保留）；`parseChatResponse` 增加 `toolCalls`，`readToolCalls` 保留原文
- `src/cli.ts` — `ask --tools`；`replay` 打印原请求带的工具与解析出的工具请求；【真实调用】/【离线回放】分别标注
- `sandbox/notes.txt`、`sandbox/todo.md` — 合成练习文件

## 运行证据

1. 真实调用 + 录制（旧解析器）：HTTP 200，`content: ""`，`tool_calls[0].function.arguments = "{\"path\": \"notes.txt\"}"`
2. 回放该 fixture：解析出 `read_file`（id 保留、参数原文保留），退出码 0 —— 离线回放
3. 回归：回放 01.3 旧 fixture，文字回答路径不受影响 —— 离线回放
4. 再次真实调用：`content` 带叙述文字，`tool_calls` 同时存在；耗时 2266 ms —— 真实运行

## 失败与反例

- 预测（学习者与我）："content 为空 → 报 `缺少 choices[0].message.content`"。实测：提供商返回空**字符串**，校验通过，旧代码安静输出空回答。该错误分支只在 content 缺失/为 null 时才触发。
- 教训：分支的触发条件不能靠推测的字段形状，要用实测数据。
- 中间态插曲：观察时那行 `Cannot read properties of undefined` 是"cli 已期待 toolCalls、解析器还没给"的过渡状态，不代表旧程序行为。

## 我的判断与反馈要点

- 学习者预测"报错缺少……这行"：对代码走查正确（非字符串必抛该错）；错在前提——该提供商 content 是空字符串。
- 再次应验"本地校验只能验格式、形状由服务端决定"。
