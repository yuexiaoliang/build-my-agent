# 01.3 · 离线回放

- 日期：2026-09-14
- 本步问题：怎样在没有网络和密钥的情况下，验证程序对模型响应的处理？
- 对应蓝图：第 01 章（哪些任务需要 Agent）
- 代码快照：公开仓库 `课程(01.3)`；fixture 见 `fixtures/`
- 状态：有解释/预测证据（提出设计并被修正后采纳）；可回放正常、损坏、HTTP 失败三类

## 核心结论（可迁移）

- 回放 = 把响应存成数据、替换“响应从哪来”，解析路径一行不改。
- fixture 结构：**信封（我们定义的客户端事实：录制时间、耗时、状态码、请求内容、会话 ID）+ 原始响应体（原样文本）**。
- 不要把 `content`、`usage` 归一化后存进 fixture：那等于拿被测代码的输出当输入，解析路径永远不会被回放到，还会抹掉第 04 章要讲的协议差异。厂商差异由解析层处理，fixture 保持“事实”。
- 客户端才能观测到的事实（时间、耗时、状态码）不在厂商响应体里，必须由我们记录。
- 失败也要录：录制发生在解析之前，因此 401 这类错误可以回放，不必再次花钱触发。
- 回放能证明协议解析、错误分类、状态更新；不能证明模型能力与真实可用性。两种模式必须在输出中分别标注（已实现：【真实调用】/【离线回放】）。

## 关键代码与入口

- `src/model.ts`：`sendChatRequest`（网络那半段）与 `parseChatResponse`（解析那半段，纯函数）
- `src/fixture.ts`：`writeChatFixture` / `readChatFixture`（含结构校验，拒绝不符合约定的文件）
- `src/cli.ts`：`ask [--record <file>]`、`replay <file>`、`config`
- `fixtures/chat-2026-09-14.json`（真实成功录制）、`fixtures/chat-401-model-not-supported.json`（真实失败录制）、`fixtures/chat-malformed.json`（手工构造的损坏响应）

## 运行证据

1. 真实调用并录制：332 tokens，4267 ms，落盘 2.4 KB
2. 回放成功 fixture：输出与真实调用一致，明确标注【离线回放】
3. 回放时故意把 base URL 指向 `127.0.0.1:9`：仍然成功 → 证明回放不读配置、不联网
4. 回放 401 fixture：HTTP 401 + 服务端原文，退出码 3
5. 回放损坏 fixture：`响应不是合法 JSON`，退出码 4
6. 安全检查：录制文件不含 `authorization` / `bearer`（grep 计数 0）

## 失败与反例

- 反例（本步讨论中被否掉的方案）：fixture 存成 `{content, usage, 耗时, 模型名}` 的归一化结构——回放永远测不到“厂商原文 → 内部结构”这段解析代码。

## 我的判断与反馈要点

- 我的提案：不要一刀切存整个响应，改用自定义 schema 存 content、token 统计、请求/响应时间、模型名，以兼容不同 provider。
- 反馈：容器思路正确（客户端事实必须自存）；但 content 与 usage 属于解析结果，不能存进 fixture——否则回放跳过被测代码，并抹掉协议差异。
