## 核心结论（可迁移）

- 一轮多请求是合法且常见的行为：指定"一次发起两个读取"后，模型一次响应两个 `read_file`（`index` 0/1，`id` 各自独立）。
- 关联由 `tool_call_id` 决定，**位置不参与判分**：把两条 tool 消息颠倒顺序发出（id 不变）→ HTTP 200 接受，模型仍正确对应两份内容。
- 与 03.1 合起来：服务端强制的是"每个结果都有出处"（缺配对 → 400），不是"出处按顺序排"（乱序 → 200）。
- `index` 是位置标号（非流式里等于数组下标）；流式分片重组才是它的主场（08 章）。Harness 保持数组序执行/回填是最省事的选择。
- 边界：只验证了当前提供商、非流式；不能推广为普遍保证（其他提供商在 24 章复核）。

## 关键代码与入口

- `src/model.ts` —— `ToolCall.index`（读取线上字段，缺省回落数组下标）
- `src/cli.ts` —— 播报与 replay 输出 `[index=…]`
- `scripts/reversed-tool-messages.ts` —— 从 fixture 重建第 2 轮请求、把 tool 消息颠倒后发送（复用回放基建）

## 运行证据

- 真实运行：`ask --tools "同时读取 notes.txt 和 todo.md…"` → 第 1 轮两请求按序回填；第 2 轮模型分别总结、对应正确；累计输入 960 + 输出 180；fixtures `chat-2026-09-15-multitool.json`、`…-round2.json`
- 边界实验：`node scripts/reversed-tool-messages.ts` → HTTP 200、模型对应正确（584+105 tokens）；fixture `chat-2026-09-15-multitool-reversed.json`
- 离线回放：`replay` multitool fixture → 两个调用各带 index 与 id
