# 03.1 · 工具结果回填与调用 ID 关联

- 日期：2026-09-15
- 本步问题：工具执行完之后，模型怎样才能看到结果并继续行动？
- 对应蓝图：第 03 章 Agent Loop（如何根据观察继续行动？）
- 代码快照：提交 `课程(03.1)`
- 状态：有解释或预测证据

## 核心结论（可迁移）

- 模型无记忆：每次调用都是独立 HTTP 请求，"继续行动"= Harness 把历史装进新一轮 messages。
- 回填三条消息缺一不可：`user`（问题）→ `assistant`（模型上轮原话，含 tool_calls，id 在此）→ `tool`（结果，带 `tool_call_id` 指回去）。
- id 关联是服务端强制的结构校验：tool 消息前面没有带 tool_calls 的 assistant → HTTP 400，请求到不了模型。
- 被拒绝的调用也要回填（`tool_call_id` + 拒绝原因），否则 id 配对断裂，下一轮同样 400。
- 提供商在模型前有一层校验，相当于对方的 Harness；我们的闸门（02.3）守卫文件系统，它守卫模型输入。
- 代价可见：第二轮输入 465 tokens > 第一轮 364——无记忆意味着每轮重发全部历史（14 章处理）。

## 关键代码与入口

- `src/model.ts` —— `ChatMessage` 改为联合类型（user/system、assistant 带 toolCalls、tool 带 toolCallId）；新增 `toWireMessage` 在发送前序列化为协议线格式（`tool_calls` / `tool_call_id` 下划线命名只出现在线上格式里）。
- `src/cli.ts` ask —— 执行完工具后收集 tool 消息（拒绝也回填），组装三条消息发第二轮；第二轮若模型还要工具则打印并停止（有界循环留 03.2）。
- `scripts/orphan-tool-message.ts` —— 失败路径实验：跳过 assistant 发孤儿 tool 消息。

## 运行证据

- `node src/cli.ts ask --tools "…notes.txt 写了什么…"`（改造前，真实运行）→ 模型请求 read_file，内容只打印未回填，用户要的总结没出现；fixture `chat-2026-09-15-loop-before.json`。
- 同一命令（改造后，真实运行）→ 第二轮 messages = user(29) + assistant(39 字符，含 tool_calls) + tool(76)，模型基于文件内容给出总结；输入 360→464 tokens；fixtures `chat-2026-09-15-loop-after.json` 与 `…-round2.json`（数字按仓库当前 fixtures 复跑录制刷新）。
- `node scripts/orphan-tool-message.ts`（真实运行）→ HTTP 400："Messages with role 'tool' must be a response to a preceding message with 'tool_calls'"；fixture `chat-2026-09-15-orphan-tool.json`。

## 失败与反例

- 孤儿 tool 消息被 HTTP 400 拒绝：证明 id 关联由服务端结构校验强制执行，不是模型自行解读。

## 我的判断与反馈要点

- 设计题回答正确：三条消息、id 一一对应、存在 tool 角色，三点都成立；唯一缺口是漏了 assistant 消息的必要性（id 指向的调用记录必须在场）。
- 失败路径预测选 C（服务端默默丢弃、只按 user 回答），理由"messages 是喂给 AI 的，服务端没做这方面控制"；实测 B（HTTP 400）。误解点：忘了提供商在模型前有校验层——01.2 的 401 已是反例但未迁移过来。
