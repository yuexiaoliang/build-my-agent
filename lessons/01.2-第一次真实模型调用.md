## 核心结论（可迁移）

- 一次模型调用就是一次 HTTP 请求：`POST {baseUrl}/chat/completions`，请求体只有 `model` + `messages`，密钥走 `Authorization: Bearer`。不需要 SDK，也不需要框架。
- 本地只能校验"变量填没填"，不能校验"值对不对"。密钥是否有效、模型是否存在，只有服务端能判定；**本地检查通过 ≠ 调用可用**。
- 失败必须分类，否则排查时无从下手：缺配置（退出码 1）、HTTP 错误（3）、响应结构不可用（4）、其他网络/运行时错误（5）。
- 错误码不能想当然：未知模型返回 **401** 而不是 400，网关把"模型不支持"归到了授权/路由一类。
- 供应商有请求约定：OpenCode Go 要求 `x-opencode-session`（稳定会话 ID）并自报 User-Agent，缺了直接 400。这类要求只能从服务端错误信息里学到。

## 关键代码与入口

- `src/config.ts` `readModelConfig`：必填三个变量，返回缺失清单；只打印变量名和密钥长度，不打印值
- `src/model.ts` `chat`：一次 POST，返回 `text / model / usage / elapsedMs / sessionId`
- `src/cli.ts` `ask`：先打印请求目标、模型、会话 ID，再打印回答与用量
- 环境变量优先于 `.env`，因此失败实验可以不改 `.env` 直接跑

## 运行证据

1. 无 `.env` 或值为空 → `缺少配置：MODEL_BASE_URL、MODEL_API_KEY、MODEL_NAME`，退出码 1（本地失败）
2. 首次真实调用 → HTTP 400 `Request is missing x-opencode-session`（真实失败，暴露供应商约定）
3. 补上会话头后成功 → 49 输入 + 286 输出 = 335 tokens，6181 ms；回答正确解释了模型与 Harness 的分工
4. `MODEL_NAME=not-a-real-model` → HTTP 401 `Model not-a-real-model is not supported`
5. `MODEL_API_KEY=invalid-key-for-test` → HTTP 401 `Invalid API key.`

以上均为真实运行；本步尚无离线回放。

## 失败与反例

- 反例：以为"配置就绪"就等于能调用成功——第 3 次运行才暴露出会话头要求。
- 反例：以为未知模型是请求格式错误（400），实际是 401。
- 两者的共同点：判据在服务端，本地无论怎么写校验都覆盖不到。

## 我的判断与反馈要点

- 我的预测：`MODEL_NAME` 写错时，base URL 和 key 正确就能到达服务商，由服务商返回错误——因为"配置检查只能知道填没填，不知道对不对"。
- 实测结论：判断成立；补充细节是 401 而不是 400，说明错误码分类也属于"服务端事实"，不能靠常识推断。
