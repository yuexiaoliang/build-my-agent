# 第 01 章汇总 · 任务与模型

- 日期：2026-09-14
- 本章核心问题：哪些任务需要 Agent？
- 章末 tag：`ch01`（公开仓库）；各步细节见 01.1–01.3 卡片

## 每一步给出的部分答案

- **01.1 任务形态**：判据是"下一步做什么能不能提前写死"。能写死 → 普通程序或固定工作流；必须依赖运行时证据才能决定 → Agent。"用不用模型"不是分界线。
- **01.2 一次真实调用**：调用 = 一次 HTTP 请求。本地配置检查只能验"填没填"，值对不对、能否路由由服务端判定（实测：缺会话头 400、模型名错误 401）。
- **01.3 离线回放**：把"响应从哪来"换成文件，解析路径一行不改。fixture = 信封（客户端事实）+ 厂商原文；失败也要录。

## 概念线

任务形态判据决定"要不要 Agent"（01.1）→ 一旦要，最小执行单元是一次模型调用（01.2）→ 真实调用不稳定、要花钱，所以协议处理必须能用固定响应回归（01.3）。

三层职责贯穿全章：模型负责"想"，Harness 负责"管"（本地校验、组织上下文、边界），环境负责"发生"（唯一的事实来源）。

## 应能回答的问题（自测）

1. 判断一类任务是否需要 Agent 的判据是什么？"复杂但步骤固定"算不算 Agent？
2. 哪些职责属于 Harness，哪些属于环境？为什么"模型说修好了"不算数？
3. 哪些错误本地配置检查就能发现，哪些必须由服务端判定？各举一例。
4. fixture 里为什么不能存归一化后的 `content` 和 `usage`？
5. 回放能证明什么、不能证明什么？两种模式为什么必须在输出里分别标注？
6. 要验证"越界路径必须被拒绝"这条规则：真实调用、离线回放、单元测试各能证明哪一段？（第 02 章落地）
